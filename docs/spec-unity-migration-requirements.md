# Unity 移行要件洗い出し・確定仕様まとめ

---

## 0. 確定した仕様変更（今回の会話で決定済み）

| 項目 | 決定内容 |
|------|--------|
| カスタム俳句 | **候補B（合句）**を採用。2枚の百人一首を合体して新カード生成 |
| 詠み上げレベル | 採用。`usedCount` を活かしたカード成長 |
| 筆の跡 | **ビジュアル装飾として再定義**。毛筆フォント・カードスリーブ・金地の色紙など |
| 封印（Seal） | 廃止 |
| 歌枕タイル（ジョーカー枠） | 廃止。歌枕はステージのシナジー設定として残す |

## 1. プラットフォーム・配布

### 要決定 1-A：ターゲットプラットフォーム

| 選択肢 | メリット | 注意点 |
|--------|---------|--------|
| PC のみ（Windows/Mac） | 開発コスト最小 | リーチが限られる |
| PC + モバイル（iOS/Android） | リーチ最大 | UI設計をタッチ前提にする必要あり |
| PC + WebGL（Unityで継続Web配信） | 既存ユーザー引継ぎ可 | WebGLはパフォーマンス制限あり |

> 現在の Web アプリを「廃止するか / Unity WebGL で代替するか / 並行維持するか」も合わせて決める。

### 要決定 1-B：配布先とビジネスモデル

| 選択肢 | 内容 |
|--------|------|
| itch.io（無料/有料） | 審査なし、個人開発に向く |
| Steam | 審査・登録費あり。PC ゲームの主流 |
| App Store / Google Play | モバイル選択時に必要 |
| フリー / 買い切り / 基本無料+課金 | 課金がある場合はセーブデータ設計に影響 |

## 2. Unity バージョン・レンダリング

### 要決定 2-A：Unity バージョン

| 選択肢 | 特徴 |
|--------|------|
| **Unity 6（6000.x）** | 最新。新 UI Toolkit が充実。将来性あり |
| Unity 2022.3 LTS | 実績あり。サポート期間が長い |

> カードゲームの規模ならどちらでも問題ない。新規プロジェクトなら Unity 6 推奨。

### 確定推奨 2-B：レンダリングパイプライン → **URP（Universal Render Pipeline）**

2D カードゲームには URP が最適。金地のシェーダー表現、スリーブのスプライト重ね合わせも URP で十分対応可能。Built-in は事実上レガシー。

## 3. カード表現・ビジュアルシステム

ここが最も決定事項が多い領域。

### 要決定 3-A：カードの実装方式

| 選択肢 | 特徴 | 向いている場合 |
|--------|------|-------------|
| **Canvas UI（uGUI / UI Toolkit）** | レイアウトが楽。スクロール・アニメも簡単 | カードを UI として扱う場合 |
| **ワールドスペース スプライト** | 3D 的な奥行きやカードフリップが自然 | 2.5D 演出をしたい場合 |
| **混合（ワールド空間カード + Canvas HUD）** | 両方のいいとこどり | 手間は増える |

> この選択が後のアニメーション・エフェクト設計全体を規定する。

### 要決定 3-B：カード装飾（筆の跡）の実装

「ビジュアルとしての筆の跡」を Unity でどう実現するかの選択。

**毛筆フォント（句テキスト）**
- TextMeshPro を使うのは確定
- **フォントの選定が必要**：商用利用可の毛筆フォント（例：衡山毛筆フォント、はんなり明朝など。ライセンス確認必須）
- フォントを「詠み上げレベル」や「装飾ランク」に応じて変えるか？（Lv0=普通フォント、Lv3=金泥毛筆フォント、など）

**カードスリーブ（外枠・背景デザイン）**
- スプライトレイヤーの差し替えで実現
- スリーブのデザインが何種類必要かを決める（テーマ別？レアリティ別？詠み上げLv別？）

**金地の色紙（金箔エフェクト）**
- URP Shader Graph で金箔シェーダーを作る（キラキラ・光沢）
- パーティクルで光の粒を乗せる
- スプライトのマテリアルに金色グラデーションを差し込む
- → どの程度のリッチさを目指すか（動的に輝くか、静的な金色か）

**装飾はいつ付与されるか**
- 詠み上げレベルアップ時に自動付与（Lv1→スリーブ変化、Lv3→金地）
- ショップやイベントで明示的に選ぶ（Balatro 的な選択の楽しみ）
- 両方（自動 + 任意追加）

> 装飾はゲームプレイ上の効果を持つか、**純粋なビジュアルのみか** も要確認。

## 4. アーキテクチャ移植

### 現状の TypeScript 設計と Unity C# の対応

| TypeScript（現状） | Unity C# の候補 |
|-------------------|----------------|
| `GameStore`（pub/sub） | `ScriptableObject` イベント / シングルトン `GameManager` / UniRx |
| `dispatch()` 純粋関数 | `static` メソッド or `Manager` クラスのメソッド |
| `RunState` （Plain Object） | C# `class`（参照型）or `struct`（値型）+ ScriptableObject |
| `Card` / `Poet` 型 | `ScriptableObject`（データ） + `MonoBehaviour`（表示） |
| `localStorage` | `Application.persistentDataPath` への JSON 書き出し |
| `poems-raw.ts` / `poets.ts` | JSON → Resources フォルダ or ScriptableObject |

### 要決定 4-A：状態管理のパターン

| 選択肢 | 内容 | 向いている場合 |
|--------|------|-------------|
| **シングルトン GameManager** | シンプル。小〜中規模向き | 複雑な DI が不要な場合 |
| ScriptableObject イベント | 疎結合。Unity らしい設計 | エディタ上でイベントを繋ぎたい場合 |
| VContainer（軽量 DI） | テスタブル。大規模向き | 将来の拡張を見越す場合 |
| UniRx / R3 | リアクティブ。TS の store に近い | 既存の pub/sub 設計を維持したい場合 |

### 要決定 4-B：データフォーマット（句・歌人データ）

| 選択肢 | 内容 |
|--------|------|
| **JSON → `Resources` フォルダ** | 現状 TS データをほぼそのまま移植できる。最速 |
| ScriptableObject（`PoemSO`, `PoetSO`） | Unity らしく、Inspector で編集可。移植コストが高い |
| CSV | 非エンジニアでも編集しやすい |

> 100首・100歌人のデータ量なら JSON が移植コスト最小。

## 5. セーブデータ

### 要決定 5-A：セーブ方式

| 選択肢 | 内容 |
|--------|------|
| `PlayerPrefs` | 簡単だが容量・型の制限あり。プロフィール程度なら十分 |
| **JSON ファイル**（`persistentDataPath`） | 現状の localStorage 設計をほぼ移植できる |
| クラウドセーブ（Steam Cloud / Unity Gaming Services） | 端末をまたいだ引継ぎが可能。実装コスト増 |

> 合句カードの「どのカードを合体させたか」などの複雑なデータを保存する必要があるため、JSON ファイル方式が現実的。

### 要決定 5-B：詠み上げレベルの永続化スコープ

「ランをまたいでも保持する」か「ランリセット」かはここで再確認が必要。

| 選択肢 | 体験 | セーブデータ |
|--------|------|-----------|
| **ランをまたいで保持** | 「育てたカード」への愛着。長期プレイのモチベーション | カードごとの usedCount をプロフィールに保存 |
| ランリセット | Balatro 的な「ラン内爆発」体験。シンプル | ラン終了時に破棄 |

## 7. オーディオ

### 要決定 7-A：BGM

| 選択肢 | 内容 |
|--------|------|
| フリー素材 | 実装コスト最小。クオリティは素材依存 |
| 和風フリー素材（DOVA-SYNDROME等） | 日本語フリー素材が充実 |
| オリジナル発注 | 最高品質。費用が発生 |

### 要決定 7-B：詠み上げ音声（最大の選択）

百人一首ゲームとして「句を読み上げる声」の有無は体験を大きく左右する。

| 選択肢 | 内容 |
|--------|------|
| **音声なし** | 実装コスト最小。テキスト表示のみ |
| テキスト読み上げ（TTS） | `Windows.Media.SpeechSynthesis` など OS 標準。品質は限定的 |
| ボイス収録 | 100首 × 2フレーズ = 最低200収録。費用・時間大 |

### 要決定 7-C：オーディオ実装

- Unity 標準の AudioSource で十分か
- FMOD / Wwise（高品質なSFX管理が必要な場合）

## 8. アニメーション・エフェクト

### 要決定 8-A：アニメーションの水準

| 水準 | 内容 | 工数 |
|------|------|------|
| 最小（フェード・スライドのみ） | DOTween で実装。クリーンで軽量 | 低 |
| 標準（カードフリップ、ダメージ数値） | DOTween + パーティクル | 中 |
| リッチ（憑依エフェクト全画面、金箔カード輝き） | Shader Graph + Animation + Particle | 高 |

### 憑依エフェクトについて（新機能）

憑依は「プレイヤー自身が歌人になる」演出が重要。
- 全画面フラッシュ → 歌人の肖像（イラスト）が出現 → プレイヤー名が変化
- **歌人イラストの用意が必要か** を決める（フリー素材 / 自作 / AI生成 / 発注）

## 9. 新機能と Unity の統合

### 詠み人フィールド

- バトル画面に専用スロット UI を追加（Canvas パネル）
- 歌人カードを「ドラッグ＆ドロップ」でフィールドに置くか、「ボタン選択」か

### 憑依システム

- 発動条件のチェックを `BattleManager.Update()` または `OnCardPlayed` イベントで行う
- エフェクト再生のための `PossessionEffectController` が必要

### 合句（カスタム俳句 B）

- 専用の `FusionScreen` シーンまたはオーバーレイ UI が必要
- 合体元の2枚を選択 → プレビュー表示 → 確定 の UX フロー

### 歌枕ステージ

- `DungeonDef` の拡張は C# ScriptableObject への移植で自然に実現
- ステージ選択画面のビジュアルをどう変えるか（絵巻物風か現状維持か）

## 10. 開発フロー・品質管理

### 要決定 10-A：テスト戦略

| 選択肢 | 内容 |
|--------|------|
| **なし（手動テストのみ）** | 個人開発では現実的 |
| Unity Test Framework（EditMode） | `BattleResolver` などの純粋ロジックを C# テストへ移植可 |
| PlayMode テスト | UI・シーン込みの統合テスト。工数大 |

> 現状 TS の `dispatch()` がほぼ純粋関数で書かれているため、C# でも `BattleResolver` 相当をテスタブルに保ちやすい。

### 要決定 10-B：CI/CD

- GitHub Actions + GameCI（Unity の自動ビルド）
- ローカルビルドのみ

### Git 運用上の注意（Unity特有）
- **Git LFS 必須**：テクスチャ・音声・動画等のバイナリアセット
- `.meta` ファイルはコミット対象（消すと参照が壊れる）
- シーン・プレハブは YAML テキスト形式でコンフリクトが起きやすい → 担当分けか Force Text 設定確認

## 11. 要決定事項 一覧（優先度順）

| 優先度 | 項目 | 影響範囲 |
|--------|------|--------|
| ★★★ | ターゲットプラットフォーム（PC/モバイル） | UI設計・入力・解像度 全体 |
| ★★★ | カードの実装方式（Canvas UI vs ワールドスペース） | ビジュアル・アニメーション全体 |
| ★★★ | 詠み上げレベルの永続化スコープ（ランまたぎ or リセット） | セーブ設計・バランス |
| ★★★ | 筆の跡がゲームプレイ効果を持つか（純ビジュアルのみか） | ゲームバランス・実装量 |
| ★★ | Unity バージョン（6 vs 2022.3 LTS） | 開発環境 |
| ★★ | データフォーマット（JSON vs ScriptableObject） | 移植コスト |
| ★★ | 状態管理パターン（シングルトン vs ScriptableObjectイベント vs DI） | アーキテクチャ全体 |
| ★★ | 歌人イラストの有無・素材調達方法 | 憑依・詠み人フィールドの演出品質 |
| ★★ | 詠み上げ音声の有無 | 体験品質・制作コスト |
| ★ | マップ画面のビジュアル（現状維持 vs 絵巻物風） | アート工数 |
| ★ | 配布先・ビジネスモデル | ストア申請・収益化 |
| ★ | CI/CD・テスト戦略 | 開発効率 |
